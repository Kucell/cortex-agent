# 框架通用性规则 (Framework Generality)

> **核心规则**：cortex-agent 是**通用的** agent 管理框架。它下发给受管项目的
> 一切，必须对框架从未听说过的项目同样成立。实战项目的身份——项目名、
> mission 号、主机地址、属主账号——在那个项目之外没有意义，因此把它绑进
> 框架是缺陷，不是风格问题。

---

## 为什么这不是洁癖

分发面是每一个用户的项目。实战项目的标识出现在分发文件里有三种失败方式，
**最糟的是第三种**：

1. **明显不对**——示例配置里的仓库在读者那边根本不存在。容易发现。
2. **解析到别的东西**——读者恰好有同名的项目，或同地址段的主机。示例悄悄
   指向了错误的对象。
3. **看起来是对的**——读者复制了示例，它跑起来了，而框架的默认值悄悄指向
   了别人的仓库。没有任何显式失败。这是最糟的，因为读者收不到任何信号。

第三种正是「项目名出现在分发配置示例里」最危险的原因：**示例本来就是给
人复制的**。

---

## 不得绑定的内容

| 类别 | 反例 | 正确写法 |
| :--- | :--- | :--- |
| 项目名 / slug | `repo: SamHMI` | `repo: your-repo` |
| 组织 | `org: SamkoonHMI` | `org: your-org` |
| Mission 标识 | `M-053` | 通用措辞；追溯编号放治理仓 |
| 私有主机地址 | `http://192.168.2.110:3000` | `https://vcs.example.com` |
| 个人账号 | `account: xueyq` | `account: your-account`，或运行时推导 |
| Keychain 命名空间 | `namespace: SamHMI` | `namespace: your-project` |

**要推导，不要写死。** 默认账号宁可算出来也不要猜：
`${ACCOUNT:-${USER:-$(id -un)}}` 让每个用户拿到自己的账号，而框架不必
在任何地方写死某个人的名字。

---

## 允许的情形，以及理由

并不是提到项目名就是绑定。以下是正当的：

- **框架自己的标识**。cortex-agent 的 `M-0xx`、`MS-0xx`、`VC-xxx-xxx`、
  `P-0xx` 是它自己的追溯体系，属于治理仓；提交说明里引用它们是追溯，
  而追溯正是治理仓存在的意义。
- **决策记录里的实战项目标识**。「已在 `<项目>` 实测」是有价值的事实，
  改掉它等于篡改「到底测过什么」的记录。
- **文档正文里出现的项目名**。同上。但**标题**不同：一个以实战项目命名的
  框架文档，读起来就像那个项目的一个组件——这一项会被拦截。
- **历史发布说明与已完成的执行计划**。它们记录「发布了什么」。把历史改写
  掉的历史记录，比一个提到项目名的历史记录更糟。

---

## 提交与分支卫生

同样的道理适用于框架自己的提交与分支：

- 提交的 **scope** 是稳定的模块名（`coordination`、`runtime-layout`），
  绝不是 mission 或任务号。见 `commit-standards.md`。
- **分支名**描述改动本身，不描述它是在哪个项目上验证的。
- 提交 **body** 可以引用 mission 号——那是追溯，追溯是应该的。

---

## 机械门禁

纯文字规则挡不住项目名进入分发文件，因此本规则由机械门禁强制：

| 规则 | **怎么**获得 | 门禁 |
| :--- | :--- | :--- |
| `framework-generality.md`（本文） | **是否**允许绑定 | `check-framework-generality.js` |

```bash
pnpm check:framework-generality
```

门禁扫描模板树、框架自身源码与架构文档，报告：实战项目的标识、实战
mission 号、私有主机地址、个人账号，以及出现在文档标题或文件名中的
实战项目名。

文件可以被豁免，但豁免必须写明理由：**没有理由的豁免只是门禁上的一个洞**。

## 检查清单

- [ ] 这个文件会下发给受管项目吗？
- [ ] 它是否含只有某个实战项目才讲得通的项目名、组织、地址、账号或
      mission 号？
- [ ] 这个值读者本来就要替换掉吗？
- [ ] 在另一台机器、另一个组织里的读者，会不会拿到一个**能跑但错了**的
      默认值？
